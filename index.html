Souls.house on phones

Native iPhone and Android apps that talk to the Rails app you already have. The first release is small and complete: Paulina can sign in, chat with the residents, send a photo, lose signal, and come back to find nothing lost and nothing sent twice. Bluetooth devices like the H10 come after that, on the same foundations.

01 The first release

One job: a real person can hold a real conversation with the house from a native app. Everything else stays on the website for now.

In

  • Sign in through the browser, no copying keys
  • Conversation list; open one; start one with existing residents
  • Scrollable history, Markdown and code, attachments
  • Invite a resident to answer (the manual-response controls)
  • Progress bubbles while a resident works, then the complete reply
  • Honest pending / sent / failed states, saved drafts, recovery after signal loss

Not yet

  • Push notifications — the very next milestone
  • H10 and other Bluetooth devices
  • Account and resident administration (link out to the website)
  • Full feature parity with the web
  • Token-by-token streaming — not part of this plan (see Messages)

How we'll know it works — on both real phones

Sign in without copying API keys → open and start conversations → send text and a photo → invite a resident, see progress, then the reply → kill the signal mid-send and confirm no duplicate → with the chat open, have someone post, edit and delete a message elsewhere: all three appear without refreshing → suspend and resume, expire the login, revoke the device: each recovers or asks cleanly to sign in, and never shows another account's data.

Why native, not React Native or Hotwire Native

You asked for a proper native Souls.house on both phones. Swift/SwiftUI and Kotlin/Compose are each platform's own first-choice toolkit, and the future Bluetooth work (Core Bluetooth, Android BLE, Polar's SDK) is native either way. React Native was the main alternative (faster releases). Hotwire Native is out, as you pointed out, because the web app is Svelte, not Hotwire. Mira and I both drifted toward smaller versions of your idea during the thread; this plan is back at your size.

Builds happen on your Mac (Xcode is Mac-only). Code can be written anywhere; Xcode's command-line tools mean the Mac mostly builds and signs rather than being driven by hand.

Why the web's page data isn't reused as the API

Inertia page props are shaped for one screen and can carry web-only or sensitive fields. The phone gets an explicit, small contract. Both the web controllers and the API call the same underlying operations, so shared operations and shared tests keep them from drifting apart (it reduces drift; it doesn't prove it), but the shapes on the wire are chosen on purpose.

03 Signing in

Standard mobile OAuth (authorization code + PKCE) using the Doorkeeper gem. It feels like "Sign in with…" on any app:

  1. Tap "Sign in". The phone opens the system browser sheet at souls.house.
  2. Sign in there if needed, then approve "Souls.house app on Paulina's iPhone".
  3. The browser hands back a one-time code, never a key, and the app swaps it for tokens.
  4. Short-lived access token + rotating refresh token with reuse detection, stored in the phone's keychain / keystore. Doorkeeper supports this; our configuration still has to be validated against that requirement, not assumed from installing it.
  5. Each phone is its own named session, visible and revocable from the website.
Why not reuse the existing key-approval flow

There's already a "request a key, approve it in the browser" flow, which the residents use. I first suggested hardening it for phones. On review, making it safe (one-time code, verifier, expiry, replay and race protection, revocation) is just rebuilding OAuth's code + PKCE flow badly, so I switched to Mira's proposal. Resident API keys stay exactly as they are. Both routes end up in the same user / account / permissions context, and a phone token can never quietly get more access than the person who approved it.

Live updates need the same care: Action Cable currently authenticates with the browser cookie, so it gains a bearer-token path that keeps the token's account scope, and drops the connection when a device is revoked or someone leaves an account.

04 How messages move

Replies arrive as complete messages, not token streams. While a resident works, the apps show server-reported progress, kept visibly separate from posted messages: progress is not a partial reply. Messages can still be edited or deleted, and the apps reconcile those changes. Any "typing" effect is animation the phone draws.

Sending

The phone gives each message its own ID before sending. If the signal drops and it retries, the server recognises the ID and doesn't post it again.

→

Staying live

While a chat is open, the server sends a small "this conversation changed" nudge on any new message, edit or delete. The phone then fetches the real state.

→

Coming back

After sleep or lost signal, the phone refetches and reconciles, including edits and deletions to older messages. Offline is shown honestly as offline.

The one subtle backend change

Today a subscriber to a chat is told about messages that existed when it subscribed. The web re-subscribes whenever its message list changes, which covers most of this; a phone subscribing once would miss edits to messages created after it opened the chat. Fix: chat-level invalidations covering creation, edits and deletions. They're nudges, not data: the phone refetches authoritative state, and reconciles again after reconnecting or returning to the foreground. The subscribe-then-fetch handshake also has to be pinned down so a nudge landing mid-fetch isn't lost. A "dirty" flag plus a follow-up fetch is one candidate; the backend and client specs must define and test it.

Streaming: you'd already switched token streaming off, and nothing on master calls it any more. My review got this wrong at first. The plan is complete messages plus progress bubbles, with no chunk machinery at all.

05 Changing the API without breaking old apps

Old versions of the app will stay on people's phones for months. The rules that keep them working:

Allowed in v1 at any time

  • New optional fields
  • New optional parameters, same defaults
  • New endpoints
  • New enum values (apps must tolerate unknown ones)

Never in v1

  • Renaming a field or changing its type
  • Making something optional required
  • Changing ordering or null rules silently

If we ever need a real v2, only the edges get copied: a thin adapter translates the old shape into the same shared operation. No duplicated controller tree, no versioning framework.

v1 adapterold shape
v2 adapternew shape
One shared operation

Minimum-build floor: each app sends its build number; below the floor the server answers "please update" with a store link. A floor is only raised once the new build is actually available to the affected users on that platform (staged rollouts, regions and OS eligibility all count), so nobody gets stranded. Proposed target, not yet policy: at most two major contracts supported at once, with a published retirement window.

How it's tested

An OpenAPI description of just the mobile-facing part; shared JSON fixtures that both apps' test suites decode; and compatibility tests that run the oldest supported contract against the current server, because schema checks alone don't catch a change in permissions or ordering. Client version telemetry tells us who's still on old builds.

07 Roadmap

0 · Agree the plan — now

Scope, sign-in choice, API compatibility rules. This page.

1 · Backend foundations

Doorkeeper, chat contract gaps, retry-safe sends, Cable auth and change events, with tests. Web unaffected.

2 · Same thin slice on both phones

Sign in → list → open conversation → send → see the reply. Built side by side so the two apps stay honest with each other.

3 · Make it hold up

Attachments, history paging, inviting residents, progress bubbles, interruption recovery. Run the acceptance test on real phones.

4 · Test release

TestFlight and a Play internal track for Paulina and the house. Needs the developer accounts.

5 · Push notifications

Residents often reply minutes later, so a chat app without notifications is only half useful. First thing after the proof of concept.

6 · Towards full parity

Expand toward the agreed full-parity goal, prioritising the remaining screens with you.

7 · Bluetooth: H10 first

Capture → durable local queue → authenticated upload → explicitly permitted agent access. The reason the idea started. Whether this comes before or after parity is your call (see Choices).

09 Choices for Daniel

Is the first release the right size? Chat only, with no push notifications and no H10. Is that a real product for Paulina, or too thin to learn from?
H10 before or after parity? The roadmap puts broader parity first and Bluetooth after. If the H10 is what you want in hand soonest, that order flips.
Two native codebases from day one. We're building the same slice twice, in parallel. Does that match your experience of what keeps two apps from drifting apart, or would you build one first?
Doorkeeper. It adds a real dependency and OAuth tables to the Rails app. Fine by you, or have you been bitten by it?
Who's in the first test group, and which phones and OS versions do we have to support? That sets the minimum iOS / Android versions.
Developer accounts. Personal or company (Swombat Ltd) Apple and Google accounts? It affects the name shown in the stores and the Play testing rules.
